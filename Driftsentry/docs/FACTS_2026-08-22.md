## Chapter 1 — Introduction

**What DriftSentry does today.** DriftSentry is a local desktop detector for
behavioural rug-pull attacks against Model Context Protocol servers. It sits as a
transparent stdio proxy between an MCP client and its servers, captures a
behavioural baseline for each tool at the moment the user approves it, and
re-verifies that baseline on a schedule using probes whose values are derived
from a locally held secret key and never repeated. It scores drift
deterministically — arithmetic and regular expressions only, with a pre-trained
sentence-embedding model used as a fixed feature extractor and no language model
anywhere in the decision path — across eight signals: embedding distance scaled
by each tool's own learned variance, per-field value change, exact-equality break
on provably deterministic probes, response structure, error behaviour,
differential security rules, process-level side effects, and definition hashing.
It raises attributable alerts with before/after evidence and per-cause
mitigations, and can optionally quarantine a server.

**What it does not do.** It cannot detect a server that was already malicious
when approved (Trust On First Use). It does not contain or sandbox a server, only
observe it. It supports stdio transport only, so remote HTTP MCP servers get no
process-level evidence. Its side-effect monitor polls at 20 ms and will miss
activity between polls. It has never been tested against a real community MCP
server, and no real MCP client has driven it end to end.

**Research questions — unchanged.** RQ1 detection of definition-invariant rug
pulls; RQ2 false-alarm rate including benign updates; RQ3 gain over a hash-only
control; RQ4 adaptive probe-aware evasion; RQ5 determinism.

⚠ **Scope has widened** since the proposal in one respect worth stating: the
system now has **two detection channels**, active probing and passive observation
of genuine traffic, where the proposal described only active probing.

## Chapter 3 — Methodology and design

⚠ **Design decisions changed on 22 August:**

| Decision | Proposal | Now | Reason recorded in code |
|---|---|---|---|
| Probe values | Fixed seeded pool | **HMAC-keyed, rotated per cycle** | The pool is enumerable; the L4 attacker recognised 100% of it |
| Baseline unit | Exact argument → exact response | **Template family → behavioural invariants** | Dynamic values make exact comparison invalid |
| Response embedding | Raw response text | **Arguments redacted first** | Tools echo their input; without redaction the vector measures the probe generator |
| Detection channels | Active probing | **Active + passive** | A probe-aware server can be honest for every canary |
| Volatile fields | Not addressed | **Learned from repeated samples** | Field-level sensitivity is unusable without it |

**Hardware/software requirements — unchanged** except: pytest added as a dev
dependency; still no new runtime dependency (HMAC, CSV, statistics are stdlib).

**Version control** ⚠: single Git repository, two top-level folders, private on
GitHub. Last commit 2 August; **46 uncommitted paths** as of today.

⚠ **New risk:** six of the signals added on 22 August can raise the false-alarm
rate, and only two are currently active in the scoring path. The remaining four
require calibration before they can be enabled.

### Six attack families — unchanged, but all now record ground truth ⚠

| Family | Mechanism | Function | Event kind |
|---|---|---|---|
| `exfiltration` | Copies answer to a local sink, reads decoy `.env`; answer unchanged | `_exfiltrate` | `exfiltrate` |
| `silent-tamper` | Regex-rewrites one detail (email, `ACC-\d+`, street number) | `_silent_tamper` | **`tamper`** ⚠ new |
| `content-injection` | Appends instruction addressed to the assistant | `_content_injection` | **`inject`** ⚠ new |
| `new-egress` | Opens and holds TCP to `127.0.0.2` | `_new_egress` | `egress` |
| `sleeper` | Gate-only; delivers content-injection after trigger | `should_fire` L3 path | **`inject`** ⚠ new |
| `conditional` | Gate-only; delivers exfiltration when input matches `_INTERESTING` | `apply_attack` | `exfiltrate` |

### Five levels — **L1–L5**, confirmed (not L0–L4)

| Level | Exact rule in `should_fire()` |
|---|---|
| L1 | `return True` — every call |
| L2 | `rng.random() < scenario.stochastic_rate` |
| L3 | `trigger.tripped` OR past `trigger.after` date OR `call_index >= after_calls` OR input contains a trigger token |
| L4 | Always fires **except** when `looks_like_a_probe(arguments)` |
| L5 | As L4, plus payloads length-matched to minimise measurable drift |
